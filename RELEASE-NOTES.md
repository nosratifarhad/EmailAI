# EmailAI 1.3.1 - Release Notes

**Windows x64 · `EmailAI-Setup-1.3.1.exe` · `EmailAI-Setup-1.3.1.exe.sha256`**

This release makes the **release identity** hold from end to end. Until now the pipeline derived
everything from `desktop/package.json` but never compared it with the Git tag, so `v1.2.0` and
`v1.3.0` were published carrying an installer named `EmailAI-Setup-1.1.0.exe` (a different file with
a different SHA-256 in each release) and the same static `1.1.0` release notes. One version now
identifies the tag, the package, the installer, its embedded version metadata, the checksum and the
release notes, and any disagreement stops the release before it is packaged or published.

## Version identity

| Item | Value |
| --- | --- |
| Application version | `1.3.1` (`desktop/package.json`, the single source of truth) |
| Git tag | `v1.3.1` |
| Installer | `EmailAI-Setup-1.3.1.exe` |
| Checksum file | `EmailAI-Setup-1.3.1.exe.sha256` |
| Platform | Windows x64, per-user NSIS installer, unsigned |

## Changes in this release

* **One version identity for the whole release.** `desktop/scripts/release-version.js` resolves the
  version and the installer name from `desktop/package.json` and refuses a tag that disagrees with
  it; `desktop/scripts/verify-release.js` exposes the same checks as a standalone gate that the
  release workflow runs *before* the build (tag vs package, tag vs commit) and *after* it (exactly
  one installer named for the version, its `.sha256` matching that exact file, the version embedded
  in the installer, the generated release notes); `desktop/scripts/release-notes.js` generates the
  published release body for that version from the real Git history since the previous release tag.
* **The release workflow is fail-closed.** `desktop/package.json` and its lock file now declare
  `1.3.1` (the version the next tag must name) instead of the `1.1.0` they had kept since the first
  release, the installer and checksum are uploaded and published by their exact verified names -
  never a `EmailAI-Setup-*.exe` wildcard that could pick up a stale file - and the GitHub Release is
  titled `EmailAI 1.3.1` with the generated notes as its body.
* **Regression suite.** `tests/EmailAI.Tests/ReleaseVersionTests.cs` runs the real gate against a
  matching tag, a mismatching tag, a tag that is not `vX.Y.Z`, a tag that points at another commit,
  an installer named for another version, a checksum that belongs to another file, a missing
  checksum file, an installer without version metadata and release notes for another version - and
  fails on any hard-coded version literal in the release machinery.

No application behaviour changed in this release: the mailbox, the AI actions, the conversation
threads, the notification feed and the settings surface are exactly as shipped in the `v1.3.0`
release (which contained the conversation/thread work and the `v1.2.0` custom-folder work).

## Validation

The release pipeline (`.github/workflows/release.yml`, and the same `npm run release` locally) runs
these gates in order and publishes nothing when any of them fails:

| # | Gate | What it proves |
| --- | --- | --- |
| 1 | Tag/package identity | the tag that triggered the run equals `desktop/package.json` (and its lock file), and the tag points at the commit being built |
| 2 | Tests | `dotnet test EmailAI.slnx -c Release` - the full offline suite |
| 3 | Build | `dotnet build EmailAI.slnx -c Release` - 0 warnings / 0 errors |
| 4 | Publish | `dotnet publish src/EmailAI.Api -c Release -r win-x64 --self-contained true`, without `appsettings.Development.json` |
| 5 | Package | `electron-builder --win nsis` into a cleaned `desktop/dist/` |
| 6 | Scan | `node scripts/verify-secrets.js` - no secret, no development-only configuration and no non-placeholder Exchange/AI endpoint in the publish or in the packaged backend |
| 7 | Artifact | exactly one installer named `EmailAI-Setup-1.3.1.exe`, the `.sha256` written from that exact file and matching it, the version embedded in the installer equal to `1.3.1`, the packaged backend being the fresh publish, and `desktop/dist/RELEASE-NOTES.md` describing `EmailAI 1.3.1`, that installer and that checksum |

The gate is also exercised directly against planted defects by
`tests/EmailAI.Tests/ReleaseVersionTests.cs`, so a regression in these checks fails the pull-request
check `Verify pull request` instead of reaching a release.

| --- | --- |

| Verify a download | `Get-FileHash .\EmailAI-Setup-1.3.1.exe -Algorithm SHA256` and compare it with the published `.sha256` asset |

The published release body is generated by the pipeline for the version it releases and contains the
SHA-256 of the exact installer that was uploaded, so the notes, the title, the assets and the
checksum always describe the same build.

## Security

* Secrets (the Exchange password and the AI API key) live **only** in the Windows Credential Manager,
  under the targets `EmailAI/Exchange` and `EmailAI/AI` - never in the settings document, the
  installer, a log or an API response.
* Email HTML is treated as untrusted: it is sanitized and rendered in a sandboxed, script-less frame.
* Notification payloads contain no message body and no credential.
* The AI provider receives no credential other than its own API key.

## Known limitations

* The installer is not code-signed, so Windows SmartScreen may warn: *More info → Run anyway*.
* The install is per user and needs no administrator rights.
* This release is Windows x64 only - there is no x86 or ARM64 build.
* Mail is read + reply only in this version: summarize, suggest a reply and generate a reply draft,
  with a reply leaving the application only when **Send reply** is pressed. No marking, moving,
  deleting or composing new mail; notifications are per user and can be disabled.
* Email text of an action you trigger is sent to the OpenAI-compatible provider you configured -
  point `AI_BASE_URL` only at a provider you trust with your mail.
